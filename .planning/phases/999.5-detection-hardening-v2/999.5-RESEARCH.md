## Summary

This phase closes five concrete detection gaps in `privguard/detection.py` and `privguard/cli.py`. All five gaps were reproduced and root-caused by running the actual regex patterns against the stress-test corpus (`texto_com_pii.txt`) and synthetic fixtures. No external library changes are needed; the entire phase is pure Python stdlib.

The changes divide into three tiers of effort. The two regex fixes (CEP dot-variant, IBAN space-separated) are single-line PATTERNS changes. The two leniency extensions (CNPJ lenient, boleto barcode) require small additions to existing leniency scaffolding. Name detection is the largest change: it requires a new `detect_names()` function, a data directory with committed name files, pyproject.toml wiring, and a new `detect_names` parameter threaded through `detect()`, `mask_text()`, and all three CLI commands.

**Primary recommendation:** Implement in dependency order — PATTERNS changes first (no risk), leniency extension second, then boleto, then name detection (highest surface area).

## Gap-by-Gap Analysis

### Gap 1: CEP Dot-Variant

**Current code (detection.py line 181):**
```python
PatternEntry("BR_CEP", re.compile(r"\b\d{5}-?\d{3}\b"), 0.72),
```

**Problem verified:** `14.025-580` (from BLOCO 4 of stress test) — current regex requires 5 consecutive digits before the hyphen. The dot splits them into `14` + `025`, so `\d{5}` fails.

**Exact fix:**
```python
PatternEntry("BR_CEP", re.compile(r"\b(?:\d{2}\.\d{3}|\d{5})-?\d{3}\b"), 0.72),
```

**Verified behavior (from research_999_5.py):**
- `01310-200` (standard): matches `01310-200` ✓
- `01310200` (bare): matches `01310200` ✓
- `01.310-200` (dot-variant): matches `01.310-200` ✓
- `14.025-580` (stress test): matches `14.025-580` ✓

**Regression risks:**
- `\d{2}\.\d{3}` is a 6-char prefix ending with a digit group — unlikely to create new false positives outside of CEP contexts.
- Values like `12.345` in price contexts do not match because the full pattern requires `-?\d{3}` suffix.
- No validator change needed; CEP has no checksum.

**Edge case:** The original `\d{5}-?\d{3}` also matched bare 8-digit sequences (`\d{5}\d{3}`). The new pattern preserves this via the `\d{5}` branch. Confirmed: `01310200` still matches.

### Gap 2: CNPJ Leniency

**Current code (detection.py lines 208-210):**
```python
_LENIENT_KINDS: frozenset[str] = frozenset({"BR_CPF"})
_LENIENT_SCORES: dict[str, float] = {"BR_CPF": 0.75}
```

**Lenient block in detect() (lines 228-236):**
```python
if use_lenient and entry.kind in _LENIENT_KINDS:
    # Formatted-only guard: bare 11-digit CPF must stay strict
    if "." in value and "-" in value:
        raw.append(Hit(entry.kind, m.start(), m.end(), value,
                       _LENIENT_SCORES[entry.kind], "lenient_pattern"))
continue
```

**Exact fix:**
```python
_LENIENT_KINDS: frozenset[str] = frozenset({"BR_CPF", "BR_CNPJ"})
_LENIENT_SCORES: dict[str, float] = {"BR_CPF": 0.75, "BR_CNPJ": 0.75}
```

The existing format guard (`"." in value and "-" in value`) already works for CNPJ. Verified:
- `11.222.333/0001-00` contains both `.` and `-` → lenient hit emitted ✓
- `11222333000100` (bare 14-digit) contains neither → strict, no lenient hit ✓

**Lenient score choice:** 0.75 mirrors CPF. This is below the strict 0.95 CNPJ score. Within Claude's discretion.

**Regression risks:**
- None to existing CPF behavior — `_LENIENT_KINDS` is now a 2-element frozenset, same iteration.
- The CNPJ pattern `\b(?:\d{2}\.\d{3}\.\d{3}/\d{4}-\d{2}|\d{14})\b` matches formatted CNPJs with both `.` and `/` and `-`, so the format guard's `"." in value and "-" in value` catches all formatted CNPJs (the `/` is also present but not checked — that is fine, the check is a minimum guard).

**Important:** The format guard checks for `.` AND `-` in `value`. A formatted CNPJ like `98.765.432/0001-21` has both. The bare 14-digit `98765432000121` has neither. This matches D-03 exactly.

### Gap 3: IBAN False Positive Fix

**Current code (detection.py line 177):**
```python
PatternEntry("IBAN", re.compile(r"\b[A-Z]{2}\d{2}[A-Z0-9]{12,30}\b"), 0.90),
```

**Problem verified:** `DE89 3704 0044 0532 0130 00` — the current compact-only IBAN regex does not match (spaces break `[A-Z0-9]{12,30}`). BR_PHONE matches `89 3704 0044` (the `89 37...0044` portion) as a phone hit.

**Root cause confirmed:** `BR_PHONE` pattern `(?<!\d)(?:\+55\s?)?\(?\d{2}\)?\s?(?:9[\s-]?\d{4}|[2-5]\d{3})[\s-]?\d{4}\b` hits on `89 3704 0044` because `89` is a valid DDD and `3704 0044` matches `[2-5]\d{3}[\s-]?\d{4}`.

**Exact fix — add a second PatternEntry for space-separated IBANs:**
```python
PatternEntry("IBAN", re.compile(r"\b[A-Z]{2}\d{2}[A-Z0-9]{12,30}\b"), 0.90),
PatternEntry("IBAN", re.compile(r"\b[A-Z]{2}\d{2}(?:\s[A-Z0-9]{4}){3,}(?:\s[A-Z0-9]{1,4})?\b"), 0.90),
```

**Why two entries (same kind "IBAN"):** The overlap logic in `detect()` only compares spans, not kinds. If both match the same span, the higher-score one (or the one processed first when equal) is kept. Two entries with the same kind and same score — the compact entry handles unspaced IBANs, the new entry handles spaced ones. They will never both match the same text span (one requires spaces, the other requires no spaces).

**Pattern v3 verified behavior (from research_999_5b.py):**
- `DE89 3704 0044 0532 0130 00`: matches `DE89 3704 0044 0532 0130 00` ✓ (full match)
- `GB29 NWBK 6016 1331 9268 19`: matches `GB29 NWBK 6016 1331 9268 19` ✓
- `DE89 3704` (only 1 group after CC+check): NO MATCH ✓ (minimum 3 groups enforced)
- `FR76 3000 6000 0112 3456 7890 189`: matches ✓ (trailing 3-char group via `{1,4}`)
- Phone hits on the German IBAN string: NONE after IBAN match wins (score 0.90 > 0.76)

**The `{3,}` minimum matters:** Norway IBAN is 15 chars (shortest real IBAN). `CC + 2 + 3×4 = 16` chars in spaced format is the minimum. Without `{3,}`, `DE89 3704` (8 chars) would match falsely.

**Why score 0.90 wins over BR_PHONE 0.76:** The overlap filter processes hits sorted by `(-score, -(span_length), start)`. The IBAN hit at score 0.90 is processed first. BR_PHONE hit at score 0.76 overlaps with the already-kept IBAN → discarded. This is the existing logic, no changes needed.

**Regression risks:**
- False positives from the new spaced IBAN pattern: any `CC99 XXXX XXXX XXXX` sequence where CC is a valid 2-letter country code. Real-world risk is low because the pattern requires exactly 4-char groups. Regular text rarely has this structure.
- The existing compact IBAN is unchanged; no regression there.

### Gap 4: Brazilian Name Detection

**This is the largest change. It touches detection.py, cli.py, masking.py, and pyproject.toml.**

#### 4a. detect_names() function design

```python
# At module top, after imports
from importlib.resources import files as _importlib_files

_NAMES_DATA = _importlib_files("privguard") / "data"

@functools.lru_cache(maxsize=1)
def _load_name_sets() -> tuple[frozenset[str], frozenset[str]]:
    first = frozenset(
        n.strip().lower()
        for n in (_NAMES_DATA / "names_first.txt").read_text(encoding="utf-8").splitlines()
        if n.strip() and not n.startswith("#")
    )
    surns = frozenset(
        n.strip().lower()
        for n in (_NAMES_DATA / "names_surnames.txt").read_text(encoding="utf-8").splitlines()
        if n.strip() and not n.startswith("#")
    )
    return first, surns

_TOKEN_RE = re.compile(r"[^\W\d_]+", re.UNICODE)  # letter-only tokens

def detect_names(text: str) -> list[Hit]:
    first_names, surnames = _load_name_sets()
    tokens: list[tuple[str, int, int]] = [
        (m.group(0).lower(), m.start(), m.end())
        for m in _TOKEN_RE.finditer(text)
    ]
    hits: list[Hit] = []
    i = 0
    while i < len(tokens):
        tok, ts, te = tokens[i]
        is_first = tok in first_names
        is_surn = tok in surnames
        # Look-ahead: next token is a surname?
        if is_first and i + 1 < len(tokens):
            ntok, nts, nte = tokens[i + 1]
            if ntok in surnames:
                hits.append(Hit("BR_NAME", ts, nte, text[ts:nte], 0.72, "name_fullname"))
                i += 2
                continue
        if is_surn and i + 1 < len(tokens):
            ntok, nts, nte = tokens[i + 1]
            if ntok in first_names:
                # surname-first order (e.g. "Pereira Maria")
                hits.append(Hit("BR_NAME", ts, nte, text[ts:nte], 0.72, "name_fullname"))
                i += 2
                continue
        if is_first:
            hits.append(Hit("BR_NAME", ts, te, text[ts:te], 0.58, "name_first"))
        elif is_surn:
            hits.append(Hit("BR_NAME", ts, te, text[ts:te], 0.65, "name_surname"))
        i += 1
    return hits
```

**Note on kind name:** The CONTEXT.md uses `BR_NAME` (consistent with the `BR_*` namespace). The planner should confirm this vs. `PERSON_NAME` — but `BR_NAME` follows the existing naming convention.

**lru_cache on `_load_name_sets()`:** File I/O happens once per process. frozenset lookup is O(1). For the typical scan workload this is negligible. [VERIFIED: Python stdlib lru_cache behavior]

**Token regex `[^\W\d_]+`:** Matches letter-only sequences (including accented characters via `re.UNICODE`). This correctly tokenizes `Maria` from `Maria Aparecida da Silva Junqueira` and skips numbers and punctuation.

**Tiered scoring algorithm:**
- First name + adjacent surname (either order): score 0.72, reason `name_fullname`, single Hit spanning both tokens
- First name alone: score 0.58, reason `name_first`
- Surname alone: score 0.65, reason `name_surname`
- Particle tokens (`da`, `de`, `dos`, etc.): not in either frozenset → skipped

**Important edge:** The algorithm iterates tokens linearly and advances `i` by 2 when a pair is consumed. This prevents `Maria` from emitting both a 0.72 pair hit AND a 0.58 solo hit.

### Gap 5: Boleto Barcode False Positives

**Stress-test boleto string (BLOCO 9):**
```
83660000000-0 04960019073-3 30190105042-2 31239010103-4
```

**Digit analysis (verified):**
- 4 groups of `NNNNNNNNNNNN-N` (12 digits + hyphen + 1 check digit)
- Total raw digits: 48
- Format: `\d{11}-\d(?:\s\d{11}-\d){3}` — one anchor group + 3 space-separated identical groups

**FEBRABAN human-readable format:**
```
83660.00000 04960.019073 30190.105042 2 31239010103400
```
Pattern: `DDDDD.DDDDD DDDDD.DDDDDD DDDDD.DDDDDD D DDDDDDDDDDDDDD`
Total digits: 5+5+5+6+5+6+1+14 = 47

**Both formats match the combined BR_BOLETO PatternEntry (verified):**
```python
PatternEntry(
    "BR_BOLETO",
    re.compile(
        r"(?:"
        r"\b\d{44,47}\b"                                             # raw barcode
        r"|"
        r"\b\d{5}\.\d{5}\s\d{5}\.\d{6}\s\d{5}\.\d{6}\s\d\s\d{14}\b"  # FEBRABAN
        r"|"
        r"\b\d{11}-\d(?:\s\d{11}-\d){3}\b"                          # hyphen-check format
        r")"
    ),
    0.92,   # beats BR_PIS_PASEP (0.91) and BR_PHONE (0.76) directly
),
```

**Score reasoning:**
- `BR_PIS_PASEP` score = 0.91; `BR_PHONE` score = 0.76
- Score 0.92 beats both directly → no tie-breaking by span length needed
- Within the `≥ 0.90` floor set by D-10 and Claude's discretion
- 0.92 is the recommended value [ASSUMED: exact value within discretion; 0.92 chosen for clarity]

**Overlap resolution (verified logic from detect()):**
```
Sort: (-score, -(end-start), start)
BR_BOLETO at 0.92 processed first → added to kept
BR_PIS_PASEP inner match at 0.91 → overlaps kept boleto → DISCARDED ✓
BR_PHONE inner match at 0.76 → overlaps kept boleto → DISCARDED ✓
```

**Where to insert in PATTERNS:** After `BR_PIS_PASEP` and before `BR_CARTAO_SUS` (between lines 173–174), or at the end of the Brazilian ID section. Placement in PATTERNS does not affect correctness (overlap resolution is score-based), but grouping it near other Brazilian identifiers aids readability.

**Regression risks:**
- A bare 44-47 digit sequence could theoretically be a very long account number or transaction ID. Score 0.92 means it will mask aggressively. This is an accepted tradeoff (boleto sequences look like no other PII type, and a 44-digit run in any real text is almost certainly a barcode).
- The FEBRABAN format pattern `\d{5}\.\d{5}\s\d{5}\.\d{6}\s\d{5}\.\d{6}\s\d\s\d{14}` is highly specific — false positive risk is negligible.
- The hyphen-check format `\d{11}-\d(?:\s\d{11}-\d){3}` is also specific. The stress-test file confirms this is the real barcode printed format.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Name lookup | Linear scan of list | `frozenset` O(1) lookup | O(n) per token × thousands of names = visible latency |
| Data file loading | `open()` with `__file__` path | `importlib.resources.files()` | `__file__` breaks in zipimport/wheel contexts |
| Per-call file I/O | Re-read names.txt on every `detect_names()` call | `lru_cache(maxsize=1)` | File is ~50KB; re-reading on every call wastes I/O |
| Custom overlap resolution for names | Special cases in detect_names() | Emit Hit objects, let existing `detect()` overlap logic handle | Existing logic is tested and correct |
| New env-var reading helper | Any new mechanism | Exact same pattern as `_lenient_default()` | Consistency, no new surface area |

## Common Pitfalls

### Pitfall 1: Parameter name collision (`detect_names`)
**What goes wrong:** `def detect(..., detect_names=None)` shadows the module-level function `detect_names()` inside the body of `detect()`.
**Why it happens:** Same name used for both the parameter and the helper function.
**How to avoid:** Rename the helper function to `_find_name_hits()` (private, underscore-prefixed). The CLI flag stays `--detect-names` and the env var stays `PII_GUARD_DETECT_NAMES`.
**Warning signs:** `TypeError: 'bool' object is not callable` when calling `detect_names(text)` inside `detect()`.

### Pitfall 2: analyze_text() missing detect_names kwarg
**What goes wrong:** `analyze_text()` calls `detect()` but does not pass `detect_names`. CLI scan command gets no name hits even with `--detect-names`.
**Why it happens:** `analyze_text()` wraps `detect()` but its signature is not updated.
**How to avoid:** Update `analyze_text()` signature and call simultaneously with `detect()`.

### Pitfall 3: package-data not picked up without reinstall
**What goes wrong:** `importlib.resources.files("privguard") / "data" / "names_first.txt"` raises `FileNotFoundError` in editable install after adding the data directory.
**Why it happens:** `pip install -e .` does not re-run package discovery automatically; the data directory must exist before install, and sometimes a `pip install -e . --force-reinstall` is needed.
**How to avoid:** The Wave 0 task must create `privguard/data/` and files BEFORE the implementation tasks run. Include `pip install -e .` in Wave 0.
**Warning signs:** `ModuleNotFoundError` or `FileNotFoundError` on import when running tests.

### Pitfall 4: IBAN spaced-format regex matches short sequences
**What goes wrong:** `[A-Z]{2}\d{2}(?:\s[A-Z0-9]{4})+` with `+` (one or more) matches `DE89 3704` — a 2-group "IBAN" that is not a real IBAN.
**Why it happens:** The `+` quantifier allows just one group after CC+check.
**How to avoid:** Use `{3,}` (at least 3 groups) to enforce the minimum real IBAN length.
**Warning signs:** False IBAN hits on 2-word alphanumeric codes.

### Pitfall 5: lru_cache on a method vs. module-level function
**What goes wrong:** If `_load_name_sets` is an instance method, `lru_cache` does not work correctly (unhashable `self`).
**Why it happens:** `lru_cache` requires hashable arguments; `self` may not be hashable.
**How to avoid:** Keep `_load_name_sets()` as a module-level function (no `self`). This is consistent with the existing detection.py style (all helpers are module-level).

### Pitfall 6: CEP dot-variant creates false match on price strings
**What goes wrong:** `\d{2}\.\d{3}-\d{3}` might match a formatted price like `12.500-300` (unlikely but possible in accounting contexts).
**Why it happens:** `\d{2}\.\d{3}` is the same digit structure as Brazilian price formatting.
**How to avoid:** The existing `\b` word boundary anchors in the full pattern (`\b(?:\d{2}\.\d{3}|\d{5})-?\d{3}\b`) reduce this risk. The `-` separator is mandatory in the dot-variant branch (`-?\d{3}` → the `?` applies to the no-dot branch), no wait: looking at the proposed fix `\b(?:\d{2}\.\d{3}|\d{5})-?\d{3}\b`, the `-?` is shared. A price like `12.500-300` would match. Acceptable: CEP has priority 0.72 (below most other kinds), and price strings are not PII.

## Open Questions

1. **Kind name for name hits: `BR_NAME` vs `PERSON_NAME`**
   - What we know: existing BR_* namespace convention in PATTERNS; but names are not Brazil-specific
   - What's unclear: whether the placeholder in masked output should be `<BR_NAME>` or `<PERSON_NAME>`
   - Recommendation: use `BR_NAME` for consistency with the existing namespace; easy to rename later

2. **Token boundary for name pairs: how to handle particles (`da`, `de`, `dos`)?**
   - What we know: `Maria Aparecida da Silva` has particles between first name and surname
   - What's unclear: should `Maria da Silva` emit a 0.72 pair hit (skipping `da`)? Or only adjacent tokens?
   - Recommendation: for v1, only immediately adjacent token pairs. Skipping particles is a Phase 999.6 enhancement.

3. **Exact size of committed names files**
   - What we know: IBGE API confirms top 20 per sex; full 1500-name list requires dev-time curation
   - What's unclear: whether to start with a smaller curated list (e.g. 200 names) or attempt full IBGE coverage
   - Recommendation: start with API-confirmed top-20 per sex (40 total) plus well-known additional names, aiming for ~200 first names and ~100 surnames. Can expand later.
