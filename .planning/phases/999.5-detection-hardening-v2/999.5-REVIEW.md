## Summary

Reviewed the seven files changed in phase 999.5 (Detection Hardening v2): four regex fixes in `detection.py`, the new opt-in name detection subsystem (`_find_name_hits`, `_load_name_sets`), the `detect_names` parameter wired through `masking.py` and `cli.py`, the two IBGE name data files, the `pyproject.toml` package-data stanza, and 14 new regression tests.

The codebase is well-structured and the four regex hardening fixes (CEP dot-variant, spaced IBAN, BR_BOLETO, CNPJ leniency) all look correct. The opt-in name detection implementation is logically sound but has two concrete bugs: first-name-only hits (score 0.58) bypass the caller-specified `min_score` filter, and `verify_mask` runs its re-scan without `detect_names`, leaving a blind spot in verification when names were part of the original detection pass.

## Warnings

### WR-01: Name hits bypass `min_score` filter — first-name-only hits at score 0.58 always appear

**File:** `privguard/detection.py:315-317`
**Issue:** The `min_score` filter on line 315 is applied to `raw` before name hits are appended on line 317. First-name-only hits have score 0.58 and surname-only hits have score 0.65. At the default `min_score=0.6`, first-name hits (0.58) should be dropped but are not, because they are injected after the filter. Any caller who raises `min_score` above 0.65 or 0.72 will also silently receive lower-scored name hits they explicitly asked to exclude.

```python
# Current — name hits escape the filter
raw = [h for h in raw if h.score >= min_score]   # line 315
if use_detect_names:
    raw.extend(_find_name_hits(text))             # line 316-317  ← bypass
```

**Fix:** Apply `min_score` filtering inside `_find_name_hits` or filter the combined list after appending. The simplest fix is to move the filter one step later:

```python
if use_detect_names:
    raw.extend(_find_name_hits(text))
raw = [h for h in raw if h.score >= min_score]   # filter AFTER name hits
```

Alternatively, filter just the name hits at injection time:
```python
if use_detect_names:
    raw.extend(h for h in _find_name_hits(text) if h.score >= min_score)
```

### WR-02: `verify_mask` re-scans without `detect_names`, leaving a verification blind spot

**File:** `privguard/masking.py:67`
**Issue:** `verify_mask` calls `detect(masked_text, min_score=min_score)` without propagating `detect_names`. When a caller uses `mask_text(..., detect_names=True)`, name spans are detected and replaced. However, the verification re-scan runs with name detection off. This means if a masking bug left a name token in the output, the `residual_detection` check would not catch it — the function would return `verified=True` for text that still contains a detectable name.

The practical impact is low today (names are replaced by `<BR_NAME>` which won't re-trigger detection), but the contract is asymmetric: the detection pass uses `detect_names=True`, the verification pass does not.

```python
# masking.py line 67 — currently
residual_hits = [
    hit for hit in detect(masked_text, min_score=min_score)  # detect_names missing
    if not _is_safe_placeholder_residual(hit.value)
]
```

**Fix:** Thread `detect_names` through `verify_mask` and propagate it:

```python
def verify_mask(
    original_text: str,
    masked_text: str,
    hits: Sequence[Hit],
    min_score: float = 0.6,
    detect_names: bool | None = None,   # add parameter
) -> tuple[bool, tuple[str, ...]]:
    ...
    residual_hits = [
        hit for hit in detect(masked_text, min_score=min_score, detect_names=detect_names)
        if not _is_safe_placeholder_residual(hit.value)
    ]
```

And in `mask_text`, pass it along:
```python
verified, verification_reasons = verify_mask(
    text,
    masked_text,
    selected_hits,
    min_score=min_score,
    detect_names=detect_names,   # add
)
```

### IN-01: Duplicate test functions inflate test count without adding coverage

**File:** `tests/test_detection.py:355-403`
**Issue:** Eight test functions in the `# CPF Leniency Mode (999.4)` block (lines 355-403) are near-exact duplicates of tests already present in the `# Phase 999.4` block immediately above them (lines 261-347). The `_v2` variants test identical behavior against the same inputs:

- `test_lenient_cpf_detects_invalid_checksum_formatted` / `test_lenient_cpf_detects_invalid_checksum_formatted_v2`
- `test_strict_mode_is_default_no_env_var` / `test_strict_mode_is_default`
- `test_lenient_hit_has_lower_score_than_strict` / `test_lenient_hit_has_lower_score_than_strict_v2`
- `test_lenient_reason_code` / `test_lenient_reason_code_v2`
- `test_lenient_does_not_shadow_valid_strict_hit` / `test_lenient_does_not_shadow_valid_strict_hit_v2`
- `test_lenient_cpf_env_var_activates_leniency` / `test_lenient_cpf_env_var`

The `_v2` variants use a `monkeypatch` fixture for env isolation (which is better practice) and shared module-level constants (`_INVALID_CPF_FORMATTED`, `_VALID_CPF_FORMATTED`), but they cover no new cases. Running `pytest` will execute the same logic twice per scenario.

**Fix:** Remove the earlier block (lines 261-347) and keep only the `_v2` / monkeypatch-based versions, which have cleaner env isolation. Or consolidate the `_v2` variants into the existing tests by adding the monkeypatch fixture to them.

### IN-02: `_find_name_hits` score 0.58 falls below default `min_score` — design needs documenting

**File:** `privguard/detection.py:273`
**Issue:** First-name-only hits are emitted at score 0.58, which is below the default `min_score=0.6`. Once WR-01 is fixed (filter applied after appending), first-name-only hits will be dropped by default unless the caller explicitly lowers `min_score`. This may be intentional (the intent is to surface only high-confidence name detections by default), but there is no docstring on `_find_name_hits` or `detect` documenting this. A caller enabling `detect_names=True` will be surprised to get surname-only hits (0.65) but not first-name-only hits (0.58) at default settings.

**Fix:** After applying the fix for WR-01, add a comment in `_find_name_hits` noting that the 0.58 score for first-name-only hits is intentionally below the default `min_score`:

```python
# Score 0.58 is intentionally below default min_score=0.6.
# First-name-only hits are surfaced only when callers lower min_score
# or when they appear adjacent to a surname (scored at 0.72 as fullname).
hits.append(Hit("BR_NAME", ts, te, text[ts:te], 0.58, "name_first"))
```

### IN-03: High-frequency false-positive surnames in names_surnames.txt

**File:** `privguard/data/names_surnames.txt:1-25`
**Issue:** Several entries are also common Portuguese nouns or adjectives: `costa` (coast), `lima` (lime/file), `melo` (archaic for honey), `cunha` (wedge), `pinto` (spotted), `rocha` (rock), `gomes` (pl. of gombo, also a common exclamation), `dantas` (a place name used as interjection). When `detect_names=True`, these will fire on normal prose that contains these words. For example, a text mentioning "Na costa do litoral" or "uma cunha de madeira" will emit BR_NAME surname hits.

This is a known tradeoff of dictionary-based detection, and the opt-in flag appropriately gates the feature. However, there is no documentation in the data file header or in `_find_name_hits`/`detect` docstrings warning about the expected false-positive rate at word-level granularity.

**Fix:** Add a comment block to `names_surnames.txt` acknowledging the false-positive risk:

```text
# WARNING: several entries here are also common Portuguese words (costa, lima,
# cunha, pinto, rocha). Enabling detect_names=True will increase false positives
# in natural-language text. Review the scored output before taking automated action.
```
