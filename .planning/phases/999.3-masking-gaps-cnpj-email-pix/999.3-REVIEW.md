## Warnings

### WR-01: `test_rg_does_not_match_cnpj_prefix` uses an invalid-checksum CNPJ — test never verifies CNPJ is detected

**File:** `tests/test_detection.py:162-166`

**Issue:** The test input `"12.345.678/0001-90"` has a deliberately wrong CNPJ check digit (`90` instead of `95`). The `valida_cnpj` validator rejects it, so neither `BR_RG` nor `BR_CNPJ` will appear in `kinds`. The assertion `assert "BR_RG" not in kinds` passes trivially — even the pre-fix code would have passed this particular assertion in isolation if `BR_CNPJ` detection were also absent. The test does prove the RG pattern no longer fires, but it does not confirm that a _valid_ CNPJ that previously triggered the RG false positive is now correctly classified as `BR_CNPJ`.

**Fix:** Add a companion assertion (or a separate test) using a valid CNPJ that shares the `XX.XXX.XXX` prefix format:

```python
def test_rg_does_not_match_cnpj_prefix() -> None:
    """RG pattern must not capture the XX.XXX.XXX prefix of a CNPJ."""
    from privguard.detection import detect

    # Invalid checksum — neither RG nor CNPJ should fire
    hits = detect("12.345.678/0001-90")
    assert "BR_RG" not in [h.kind for h in hits], "CNPJ prefix must not be classified as RG"

    # Valid checksum — CNPJ must fire, RG must not
    hits_valid = detect("12.345.678/0001-95")
    kinds_valid = [h.kind for h in hits_valid]
    assert "BR_CNPJ" in kinds_valid, "Valid CNPJ must be detected"
    assert "BR_RG" not in kinds_valid, "Valid CNPJ must not also fire RG"
```

### WR-02: `BR_PHONE` pattern has no left-side word boundary after removing `\b`

**File:** `privguard/detection.py:178`

**Issue:** The old pattern had `\b` before `\d{2}` (the DDD); the fix correctly removed it to allow `+55DDD` without space. However, the full pattern now has **no leading anchor at all** when the optional `(?:\+55\s?)?` group is absent:

```
(?:\+55\s?)?\(?\d{2}\)?\s?(?:9\d{4}|[2-5]\d{3})-?\d{4}\b
```

When the `+55` prefix is not present, the match can begin at any digit in the text. A substring like `...29-30000` inside a longer numeric sequence could match `29` as DDD + `30000` as phone digits. The right-side `\b` prevents suffix extension, but the left is unguarded.

This is a pre-existing partial risk that was also present before the fix (the `\b` before DDD only helped when `+55` was absent), but the removal makes it explicit. Low false-positive probability in practice because the phone number format `DDD 9XXXX-XXXX` is quite specific, but could fire on e.g. numeric identifiers that happen to contain a valid Brazilian DDD prefix (11, 21, etc.) followed by 8–9 digits.

**Fix (conservative):** Add an alternation that requires either `+55` or a word boundary before the DDD when the country code is absent:

```python
PatternEntry(
    "BR_PHONE",
    re.compile(
        r"(?:\+55\s?\(?\d{2}\)|(?<!\d)\(?\d{2}\))\s?(?:9\d{4}|[2-5]\d{3})-?\d{4}\b"
    ),
    0.76,
),
```

Alternatively, as a minimal change, restore `\b` only for the no-prefix branch by making the prefix non-optional with an alternation:

```python
re.compile(r"(?:\+55\s?(?:\d{2}|\(\d{2}\))|\b\d{2})\s?(?:9\d{4}|[2-5]\d{3})-?\d{4}\b")
```

Note: if tightening this pattern risks breaking the existing test coverage, a lower-priority deferral to a dedicated phone-detection phase is acceptable.

### IN-01: New regression tests use redundant inline imports

**File:** `tests/test_detection.py:163,171,180,186,194`

**Issue:** The five new regression tests each contain `from privguard.detection import detect` as an inline import. The module-level import `from privguard import detection` is already present at line 7, and `detection.detect` is used throughout the existing tests via that import. The inline imports are redundant and inconsistent with the established pattern in the same file.

**Fix:** Remove the inline `from privguard.detection import detect` statements and call `detection.detect(...)` directly, matching the existing test style. For example:

### IN-02: `BR_PLACA_OLD` trailing `\b` after negative lookahead is non-obvious

**File:** `privguard/detection.py:181`

**Issue:** The final pattern is `\b[A-Z]{3}-?\d{4}(?![-\d])\b`. The trailing `\b` after the lookahead is not redundant — it additionally blocks matches where the character after the four digits is a word character other than `-` or digit (e.g., the letter `x` in `ABC-1234x`). The lookahead only excludes `-` and `\d`; without the trailing `\b`, `ABC-1234x` would match. The dual-layer filtering is correct but the interaction is subtle and not self-documenting.

**Fix:** Add an inline comment to make the intent explicit:

```python
# lookahead blocks continuation digits/hyphens; \b blocks letter suffixes
PatternEntry("BR_PLACA_OLD", re.compile(r"\b[A-Z]{3}-?\d{4}(?![-\d])\b"), 0.80),
```
