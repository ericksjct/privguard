# Phase 999.4: Code Review Report

**Reviewed:** 2026-05-21T00:00:00Z
**Depth:** standard
**Files Reviewed:** 5
**Status:** issues_found

## Summary

This phase introduces CPF leniency mode (`lenient=True` / `PII_GUARD_LENIENT` env var) that detects formatted CPFs with invalid checksums at a reduced confidence score. The implementation is generally correct and safe. The lenient path is well-guarded against bare 11-digit CPF shadowing of `BR_CNH`/`BR_PIS_PASEP`. The CLI wires the `--lenient` flag consistently across all three subcommands.

Three warnings were found: a subtle control-flow issue where the lenient branch can silently produce no hit without indicating why; a missing `lenient` parameter in `verify_mask` that makes direct callers of that function unable to mirror the detection mode used by `mask_text`; and unsafe `os.environ` mutation in the first set of leniency tests. Two info items cover duplicate test coverage and a magic-number score.

## Warnings

### WR-01: `verify_mask` has no `lenient` parameter — callers cannot mirror detection mode

**File:** `privguard/masking.py:54`
**Issue:** `verify_mask` calls `detect(masked_text, min_score=min_score)` with no `lenient` argument. This is fine when called from `mask_text` (the residual scan should be strict), but any direct external caller who runs `verify_mask` after a lenient `detect()` run has no way to ask the residual scan to match the same mode. The API asymmetry will confuse future callers and makes the function harder to test in isolation.
**Fix:** Add an optional `lenient` parameter with default `None` and thread it through to the internal `detect` call:
```python
def verify_mask(
    original_text: str,
    masked_text: str,
    hits: Sequence[Hit],
    min_score: float = 0.6,
    lenient: bool | None = None,
) -> tuple[bool, tuple[str, ...]]:
    ...
    residual_hits = [
        hit for hit in detect(masked_text, min_score=min_score, lenient=lenient)
        if not _is_safe_placeholder_residual(hit.value)
    ]
```
`mask_text` should continue to call `verify_mask(..., lenient=None)` (strict residual scan) so behaviour does not change for existing callers.

### WR-02: Silent no-op in lenient path when format guard fails — misleading to future readers

**File:** `privguard/detection.py:222-231`
**Issue:** When `use_lenient=True` and `kind in _LENIENT_KINDS` but the value lacks both `.` and `-` (i.e., bare 11-digit), the inner `if "." in value and "-" in value:` branch is skipped and no hit is appended. The outer `continue` on line 231 then fires, skipping the normal `raw.append`. The result is correct (bare 11-digit stays strict), but the control flow silently falls through without any signal. A future developer adding a second lenient kind with different format criteria may not notice the implicit "skip" and introduce a bug.

The construct mixes two independent concerns in one nested `if`: "should we attempt leniency?" and "does the format qualify?". This makes the intent hard to verify.

**Fix:** Extract the format guard into a helper and add an explicit comment at the no-op path:
```python
def _qualifies_for_lenient(kind: str, value: str) -> bool:
    """Return True if the match value meets the format requirement for lenient emission."""
    if kind == "BR_CPF":
        # Only formatted CPF (DDD.DDD.DDD-DD) qualifies; bare 11-digit stays strict
        # to avoid shadowing BR_CNH and BR_PIS_PASEP on the same span.
        return "." in value and "-" in value
    return False

# Inside detect():
if entry.validator and not entry.validator(value):
    if use_lenient and entry.kind in _LENIENT_KINDS and _qualifies_for_lenient(entry.kind, value):
        raw.append(Hit(
            entry.kind, m.start(), m.end(), value,
            _LENIENT_SCORES[entry.kind],
            "lenient_pattern",
        ))
    continue
```

### WR-03: Direct `os.environ` mutation in tests without `monkeypatch` — env var can leak on failure

**File:** `tests/test_detection.py:317-327`
**Issue:** `test_lenient_cpf_env_var_activates_leniency` sets `os.environ["PII_GUARD_LENIENT"] = "true"` and cleans up in a `finally` block. If the test process is killed (SIGKILL, OOM, timeout) between the assignment and the `finally`, the env var leaks into the process and may silently change the behaviour of later tests in the same run. Pytest's `monkeypatch` fixture provides guaranteed cleanup even under abnormal termination. The later set of leniency tests (lines 392-396) correctly uses `monkeypatch.setenv`.

**Fix:** Rewrite using `monkeypatch`:
```python
def test_lenient_cpf_env_var_activates_leniency(monkeypatch: pytest.MonkeyPatch) -> None:
    """PII_GUARD_LENIENT=true env var must activate leniency when lenient param is None."""
    monkeypatch.setenv("PII_GUARD_LENIENT", "true")
    hits = detect("456.789.123-45")
    kinds = [h.kind for h in hits]
    assert "BR_CPF" in kinds, "PII_GUARD_LENIENT=true must cause invalid CPF to be detected"
```

### IN-01: Duplicate CPF leniency test suite — two parallel sets covering the same scenarios

**File:** `tests/test_detection.py:261-403`
**Issue:** There are two near-identical suites testing CPF leniency mode. Lines 261-346 form one suite (with explicit `os.environ.pop` setup and `import` statements inside each test body). Lines 349-403 form a second suite using module-level fixtures and `monkeypatch`. Both suites test the same axes: invalid formatted CPF, strict default, score value, reason code, env var activation, bare 11-digit guard, and `analyze_text`. This doubles test maintenance cost and makes it harder to tell which suite is authoritative.
**Fix:** Consolidate into a single suite (keep the second set at lines 349-403 as it uses `monkeypatch` correctly), remove the first set (lines 261-347), and add the missing `analyze_text` case from the first set to the second:
```python
def test_analyze_text_lenient_returns_cpf_count(monkeypatch: pytest.MonkeyPatch) -> None:
    monkeypatch.delenv("PII_GUARD_LENIENT", raising=False)
    report = analyze_text(_INVALID_CPF_FORMATTED, lenient=True)
    assert report.counts == {"BR_CPF": 1}
```

### IN-02: Magic score constant `0.75` repeated across `_LENIENT_SCORES` dict and test assertion

**File:** `privguard/detection.py:204`, `tests/test_detection.py:289`
**Issue:** The lenient CPF score `0.75` is hardcoded in `_LENIENT_SCORES` and asserted by exact value in the test. If the score is tuned in the future, the test will break in a non-obvious way. The test at line 373 avoids this by using `< 0.95` (a relational check), which is more resilient.
**Fix:** Expose the score constant and import it in tests, or change the line-289 assertion to a relational check consistent with the v2 test at line 372:
```python
# test_detection.py line 289 — replace exact equality with relational check
assert cpf_hits[0].score < 0.95, f"lenient score must be below strict 0.95, got {cpf_hits[0].score}"
# (This also makes it consistent with test_lenient_hit_has_lower_score_than_strict_v2 at line 372.)
```
