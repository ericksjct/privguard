# Phase 999.4: CPF/CNH Leniency Mode — Research

**Researched:** 2026-05-21
**Domain:** Python detection engine — checksum bypass, env-var feature flags, false-positive risk
**Confidence:** HIGH (all findings from direct codebase inspection)

---

## Summary

Phase 999.4 adds an opt-in "lenient mode" to `privguard/detection.py` so that CPF-formatted
strings (`DDD.DDD.DDD-DD`) and CNH-formatted 11-digit strings are masked even when their
checksums fail. The problem is confirmed real: stress-testing with `texto_com_pii.txt` found
seven CPF-formatted values — six of which are synthetic/invalid (checksum fails) and zero CNH
values that pass checksum. All are silently ignored today.

The project already has a precedent for env-var feature flags: `PII_GUARD_THRESHOLD` and
`PII_GUARD_MODE` in `hooks.py`. That precedent sets the naming convention and access pattern
for the new `PII_GUARD_LENIENT` flag (or per-type variants). The detection engine is purely
`detect()` / `analyze_text()` — no config object exists today, so the cleanest minimal change
is either a parameter to `detect()` or a module-level env-var read, mirroring the existing hook
pattern.

False-positive risk for lenient CPF (`DDD.DDD.DDD-DD`) is LOW: the format requires exactly
3.3.3-2 digits, which is very specific and not shared by invoice numbers, bar codes, or dates.
False-positive risk for lenient CNH (11-digit bare sequences) is HIGH: bar-code fragments,
account numbers, and other 11-digit sequences are common, and the existing code already
guards against this by processing CNH checksum before CPF/PIS in the PATTERNS list.

**Primary recommendation:** Add a `lenient: bool = False` parameter to `detect()` and
`analyze_text()`, defaulted by reading `PII_GUARD_LENIENT=true` from the environment. Apply
leniency only to `BR_CPF` (formatted `DDD.DDD.DDD-DD`) in the initial scope; treat bare
11-digit CNH leniency as a separate decision because the false-positive cost is qualitatively
different from formatted CPF.

## Current Implementation — Key Facts

All findings below are `[VERIFIED: direct codebase read]`.

### How `detect()` Works Today

```python
# detection.py — current signature
def detect(text: str, min_score: float = 0.6) -> list[Hit]:
    for entry in PATTERNS:
        for m in entry.regex.finditer(text):
            value = m.group(0)
            # If validator exists AND fails → skip entirely (no downgraded hit)
            if entry.validator and not entry.validator(value):
                continue
            raw.append(Hit(..., entry.score, entry.reason_code))
```

The `continue` on line 206 is the exact insertion point for leniency. When `lenient=True`
for a given type, instead of skipping, the code would emit the hit with a lower score and a
distinct `reason_code`.

### PATTERNS Order and Overlap Hazard

`[VERIFIED: direct codebase read]` The PATTERNS list ordering is:

1. `BR_CNPJ` — 14-digit or formatted CNPJ
2. `BR_CPF` — 11-digit or `DDD.DDD.DDD-DD`
3. `BR_CNH` — 11-digit bare only
4. `BR_TITULO_ELEITOR` — 12-digit or spaced
5. `BR_PIS_PASEP` — 11-digit formatted or bare
6. `BR_CARTAO_SUS` — 15-digit

CPF regex `\b(?:\d{3}\.\d{3}\.\d{3}-\d{2}|\d{11})\b` includes both the formatted and bare
variant. CNH regex `\b\d{11}\b` is bare-only. The overlap resolution in `detect()` uses
score → length → position priority. A lenient-CPF bare hit (11-digit) and a lenient-CNH hit
on the same span would compete. The comment in the existing code explicitly says:

> "Skip hits whose checksum fails entirely — do NOT emit a downgraded score that would shadow
> other kinds covering the same span (e.g. BR_CPF failing checksum would block BR_CNH and
> BR_PIS_PASEP from the same 11-digit value)."

This is the core architectural tension for CNH leniency: if we emit lenient-CPF hits for bare
11-digit sequences, they will shadow legitimate CNH, PIS, and SUS detections on the same span.

## False-Positive Risk Analysis

`[VERIFIED: direct regex + live Python testing]`

### CPF Formatted (`DDD.DDD.DDD-DD`) — LOW false-positive risk

The regex `\b\d{3}\.\d{3}\.\d{3}-\d{2}\b` requires exactly 3 + 3 + 3 + 2 digits with dots
and dash in fixed positions. Testing against texto_com_pii.txt:

- `2024.001.456789-12` (invoice) → **no match** (wrong digit group sizes)
- Bar code `83660000000-0 04960019073-3` → **no match** (wrong separator positions)
- Standard dates (`15/03/2026`, `2026-03-15`) → **no match** (different separators)

The only false positive risk is a reference number that coincidentally uses 3.3.3-2 digit
grouping. This is rare in Brazilian administrative formats. `[ASSUMED]` risk is judged LOW
enough that lenient mode for formatted CPF is acceptable as opt-in.

Lenient formatted-CPF hits should receive score `0.75` (vs. `0.95` for strict) and
`reason_code="lenient_pattern"` to signal reduced confidence.

### CPF Bare (11-digit `\d{11}`) — HIGH false-positive risk, SKIP in phase scope

Bare 11-digit sequences are too common: bar codes, account numbers, timestamps. The existing
PATTERNS list already shares `\b\d{11}\b` across CPF, CNH, PIS/PASEP, and Título Eleitor.
Enabling bare lenient-CPF would create cascading shadow hits that corrupt the overlap logic.

**Decision point for the plan:** Lenient mode for CPF applies only to the **formatted** variant
(`DDD.DDD.DDD-DD`). The bare `\d{11}` path must remain strict for CPF.

### CNH Bare (11-digit `\b\d{11}\b`) — HIGH false-positive risk, SEPARATE DECISION

The CNH regex is bare 11-digit only — no formatted variant exists. In the stress-test file,
CNH candidate `04567891234` appears in context `CNH: 04567891234 (categoria B, validade...)`,
making it clear from context. A lenient pass would also catch bar-code segments
(`83660000000`, `04960019073`, etc.) — these are false positives.

**Recommended scope for this phase:** CNH leniency is a separate feature with higher risk and
must be explicitly opted in with a per-type flag or a dedicated env var. Do not include CNH
leniency in the initial implementation unless the plan explicitly addresses the bar-code
false-positive problem with a negative lookahead or context heuristic.

If included, use a separate flag `PII_GUARD_LENIENT_CNH=true` (or per-type dict) distinct from
the CPF flag, with score `0.65` (near the 0.6 default threshold).

### Other Checksum Types — OUT OF SCOPE for this phase

CNPJ, PIS/PASEP, Título Eleitor, Cartão SUS all have formatted regexes and similar false-positive
risk profiles to CPF. These should be added to leniency only after CPF is proven stable.

## Architecture Patterns

### Pattern 1: Parameter-based leniency with env-var default

The cleanest approach adds a `lenient` parameter to `detect()` with the env var as its default
source. This preserves backward compatibility (no callers break), allows programmatic override
in tests, and follows the existing `min_score` parameter pattern.

```python
# detection.py — proposed signature
import os

def _lenient_default() -> bool:
    return os.environ.get("PII_GUARD_LENIENT", "").lower() in ("1", "true", "yes")

def detect(
    text: str,
    min_score: float = 0.6,
    lenient: bool | None = None,          # None = read from env
) -> list[Hit]:
    use_lenient = _lenient_default() if lenient is None else lenient
    # Source: [VERIFIED: existing detect() structure, detection.py line 197-218]
    ...
    for entry in PATTERNS:
        for m in entry.regex.finditer(text):
            value = m.group(0)
            if entry.validator and not entry.validator(value):
                if use_lenient and entry.kind in _LENIENT_KINDS:
                    # Emit with reduced score and distinct reason_code
                    raw.append(Hit(
                        entry.kind, m.start(), m.end(), value,
                        _LENIENT_SCORE[entry.kind],
                        "lenient_pattern",
                    ))
                else:
                    continue
            else:
                raw.append(Hit(...))
```

Where `_LENIENT_KINDS` is a frozenset of kinds eligible for lenient mode (start with
`{"BR_CPF"}` for formatted-only hits; CNH would require additional per-kind score/risk
decision).

The PatternEntry can optionally receive a `lenient_score: float | None = None` field. When
`None`, the kind is not lenient-eligible. When set, it defines the reduced confidence score.

### Pattern 2: Per-type leniency via a set parameter (advanced, defer)

Allow `lenient_kinds: frozenset[str] | None` parameter. Provides maximum flexibility but
adds API surface complexity. Defer to a follow-up once the global bool is stable.

## Score Strategy for Lenient Hits

`[ASSUMED]` — based on reasoning about the existing score scale, not a documented standard.

| Kind | Strict Score | Lenient Score | Reason Code |
|------|-------------|--------------|-------------|
| BR_CPF (formatted) | 0.95 | 0.75 | `lenient_pattern` |
| BR_CNH (if included) | 0.93 | 0.65 | `lenient_pattern` |

Score `0.75` for lenient CPF ensures:
- It is above the default `min_score=0.6` threshold (it gets reported).
- It is clearly below the strict 0.95 (callers can filter by score if needed).
- It does not beat strict matches in the overlap resolution (strict 0.95 always wins).

The `reason_code="lenient_pattern"` (vs. `"checksum_valid"` for strict) lets callers and
audit logs distinguish the two confidence levels without examining the score numeric.

## Common Pitfalls

### Pitfall 1: Bare-11-digit CPF leniency shadows CNH/PIS

**What goes wrong:** If `_LENIENT_KINDS` includes bare-11-digit CPF hits, the overlap
deduplication discards valid CNH and PIS detections (CPF appears first in PATTERNS and
has higher score).

**Why it happens:** PATTERNS list order + score-based overlap resolution.

**How to avoid:** Restrict lenient CPF to the **formatted** sub-pattern only. The PatternEntry
for BR_CPF covers both `\d{3}\.\d{3}\.\d{3}-\d{2}` and `\d{11}`. A lenient hit should only
be created when the matched value contains dots and a dash.

**Implementation check:**
```python
# Inside the lenient branch, add format guard:
if use_lenient and entry.kind in _LENIENT_KINDS:
    if "." in value and "-" in value:   # formatted CPF only
        raw.append(Hit(..., _LENIENT_SCORES[entry.kind], "lenient_pattern"))
    # else: still skip — bare 11-digit CPF stays strict
```

### Pitfall 2: Lenient hits fail `verify_mask()` via residual detection

**What goes wrong:** After masking, `verify_mask()` calls `detect()` again on the masked text.
If `detect()` uses the same `lenient` parameter, there should be no residual. But if the
verification call uses strict mode (the default), and the masked text somehow retains the value,
the verification will fail.

**Why it happens:** `verify_mask()` currently calls `detect(masked_text, min_score=min_score)`
with no leniency. This is actually correct — verification should use strict mode.

**How to avoid:** No change needed; this is working as intended. Lenient hits are masked before
verification; the masked placeholder `<BR_CPF>` will not match any pattern.

### Pitfall 3: Test suite asserts that invalid checksums are NOT detected

**What goes wrong:** `test_invalid_checksum_lookalikes_are_below_default_threshold` in
`test_detection.py` currently asserts that `BR_CPF` is NOT detected for invalid-checksum CPFs.
Enabling lenient mode globally would break this test.

**Why it happens:** The test does not set `lenient=False` explicitly — it relies on the default.

**How to avoid:** Add `lenient=False` explicitly to all existing tests that rely on strict
behavior, OR ensure the env var default is `false` and the test does not set `PII_GUARD_LENIENT`.
Since tests run without setting the env var, the default behavior is preserved as long as
`_lenient_default()` returns `False` when the var is absent.

### Pitfall 4: CLI `--lenient` flag vs env-var interaction

**What goes wrong:** `--lenient` on the CLI overrides env var. But if a user sets
`PII_GUARD_LENIENT=true` in their shell and the CLI does not pass `lenient=True` to the
underlying functions, the env var governs. If CLI passes `lenient=False` when flag is absent,
it suppresses the env var.

**How to avoid:** Pass `lenient=None` (not `False`) when the CLI flag is absent. Only pass
`lenient=True` when the flag is explicitly set. `None` causes `_lenient_default()` to read
the env var.

## Anti-Patterns to Avoid

- **Emitting lenient bare-11-digit CPF hits:** Creates too much shadow-detection noise.
- **Using a class/config object for leniency config:** Over-engineering for a single bool flag.
- **Setting `lenient=True` as the CLI default:** Strict is the documented safe default.
- **Modifying `PatternEntry.validator` to be conditional:** Validators are canonical and used
  by Presidio integration too; bypass leniency in `detect()`, not in the validator.
- **Adding leniency logic to `masking.py`:** Masking operates on pre-computed `Hit` objects;
  the right layer is detection.
