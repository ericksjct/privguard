## Warnings

### WR-01: `_load_patterns` opens `pyproject.toml` a second time without error handling

**File:** `privguard/cleanup.py:68-69`

**Issue:** `_load_patterns` re-opens `pyproject.toml` unconditionally after
`_verify_repo_root` has already read it successfully. The second `open` call
has no `try/except`. If the file is removed, truncated, or made unreadable
between the two reads — a narrow but real TOCTOU window — Python propagates a
raw `OSError` or `tomllib.TOMLDecodeError` traceback rather than the project's
structured `[CLEANUP] error: ... reason=...` exit path. The symptom would be
an unhandled exception exiting with code 1 instead of the documented code 2,
breaking any caller that relies on the exit-code contract documented in `main`'s
docstring.

**Fix:**
```python
def _load_patterns(cwd: Path) -> list[str]:
    """Read [tool.privguard.cleanup].patterns. Schema-validate per Pitfall 2."""
    try:
        with (cwd / "pyproject.toml").open("rb") as handle:
            data = tomllib.load(handle)
    except (OSError, tomllib.TOMLDecodeError):
        _err("pyproject.toml unreadable on second read", "pyproject_unreadable")
        raise SystemExit(2)
    table = data.get("tool", {}).get("privguard", {}).get("cleanup")
    if not isinstance(table, dict) or "patterns" not in table:
        _err("[tool.privguard.cleanup] missing or invalid", "cleanup_table_missing")
        raise SystemExit(2)
    patterns = table["patterns"]
    if not isinstance(patterns, list) or not all(isinstance(p, str) for p in patterns):
        _err("[tool.privguard.cleanup].patterns must be list[str]", "cleanup_patterns_invalid")
        raise SystemExit(2)
    return patterns
```

### WR-02: `--apply` output header is generated by fragile string replacement

**File:** `privguard/cleanup.py:230-232`

**Issue:** The `--apply` branch produces its output by calling
`_format_dry_run(matches, skips)` and then replacing the literal string
`"[dry-run] would delete"` with `"[apply] deleting"` via `str.replace`.
This creates a hidden coupling: any edit to `_format_dry_run`'s header text
that does not simultaneously update the `replace()` call will silently produce
apply output that still reads `[dry-run]`, making it impossible to distinguish
a real deletion from a preview in the output. The test
`test_cleanup_apply_deletes_pycache` does not assert on the apply output text,
so this regression would not be caught by the current test suite.

**Fix:** Parameterise `_format_dry_run` with keyword arguments for the label
and verb, eliminating the string-replace coupling:

```python
def _format_dry_run(
    matches: list[tuple[str, Path, int, int, int]],
    skips: list[tuple[str, str]],
    *,
    label: str = "dry-run",
    verb: str = "would delete",
) -> str:
    """D-10: grouped-by-pattern preview with byte sizes."""
    if not matches and not skips:
        return f"[{label}] nothing to clean.\n"
    total_bytes = sum(m[4] for m in matches)
    lines = [
        f"[{label}] {verb} ({len(matches)} paths, {_human_size(total_bytes)} total):"
    ]
    # ... rest unchanged
```

Call site in the `--apply` branch becomes:
```python
apply_output = _format_dry_run(matches, skips, label="apply", verb="deleting")
sys.stdout.write(apply_output)
```

### IN-01: Unreachable `return` at end of `_human_size`

**File:** `privguard/cleanup.py:176`

**Issue:** The `for` loop in `_human_size` iterates over `("KB", "MB", "GB")`.
The condition `if n_float < 1024 or unit == "GB"` is always true on the final
iteration when `unit == "GB"`, so the function always returns inside the loop
for any `n >= 1024`. The `return f"{n} B"` on line 176 is dead code that can
never execute. This causes no runtime bug, but it misleads static analysers and
indicates an incomplete refactor.

**Fix:** Remove the unreachable return:
```python
def _human_size(n: int) -> str:
    """Return a human-readable byte count (e.g. '12 B', '1.5 KB', '3.2 MB')."""
    if n < 1024:
        return f"{n} B"
    n_float = float(n)
    for unit in ("KB", "MB", "GB"):
        n_float /= 1024.0
        if n_float < 1024 or unit == "GB":
            return f"{n_float:.1f} {unit}"
    # unreachable — remove the stale fallback return that was here
```

### IN-02: Anonymous tuple indices in `_format_dry_run` are fragile to maintain

**File:** `privguard/cleanup.py:187-197`

**Issue:** `_collect_candidates` stores matches as 5-tuples
`(pattern, path, file_count, dir_count, byte_size)`, but `_format_dry_run`
re-packs them into 4-tuples `(path, file_count, dir_count, byte_size)` stored
in `by_pattern`. The two different widths mean that the correct field index for
`byte_size` is `m[4]` in the outer sum (line 185) but `r[3]` in the per-pattern
sum (line 194). This is arithmetically correct today, but any future field
insertion into either tuple will silently produce wrong output because there is
no named access to catch the mismatch.

**Fix:** Replace anonymous tuples with a `dataclasses.dataclass` or
`typing.NamedTuple`. Minimal example:

```python
from typing import NamedTuple

class _MatchEntry(NamedTuple):
    pattern: str
    path: Path
    file_count: int
    dir_count: int
    byte_size: int
```

Field access then becomes `entry.byte_size` everywhere, eliminating the
dual-index ambiguity entirely.

### IN-03: `conftest.py` `sys.path` reorder silently misbehaves when `worktree_str` appears multiple times

**File:** `conftest.py:53-55`

**Issue:** The `elif` branch that repositions `worktree_str` to index 0 calls
`sys.path.remove(worktree_str)` followed by `sys.path.insert(0, worktree_str)`.
`list.remove()` removes only the first occurrence. If `worktree_str` appears
more than once in `sys.path` (possible if the virtualenv activation script or
another conftest already inserted it), one copy is moved to index 0 and a
stale second copy remains elsewhere in the path. The worktree copy will be
found first, so the functional effect is correct; however, the stale duplicate
means that `privguard` can be imported from two locations in the same session,
which can cause confusing `isinstance` failures across test boundaries where
two copies of the same class are loaded.

**Fix:** Purge all occurrences before re-inserting:
```python
while worktree_str in sys.path:
    sys.path.remove(worktree_str)
sys.path.insert(0, worktree_str)
```
